# 光域空间 · 数据库搭建规则参照

整理日期：2026-10-14（Asia/Shanghai）  
版本：v0.1.0；个人版实现，团队规则预留。  
用途：供后续技术 Agent 进行数据库设计、搭建和验收时参考。  
当前交付：规则文档；尚未开发代码、创建数据库或部署服务。

## 1. 第一版施工边界

**第一版只实现个人版。按照本文预留多人协作及团队版的数据框架，团队功能留待后续版本实施。**

个人版允许多个独立用户同时在线使用，每个用户管理自己的经营数据。“个人版”不代表整个平台只能有一位用户。

第一版必须落实：

1. 用户身份、个人经营簿及用户之间的数据隔离。
2. 已确认个人版业务范围所需的数据持久化、关联、汇总、版本检查和可恢复删除。
3. 个人内容归属于用户账号，区分个人内容和经营簿业务数据。
4. 网页与 Agent 共用业务服务，提供经授权的个人数据读取与写入。
5. 经营簿、成员、项目成员等结构性预留，使后续可以增加团队能力。

第一版的预留方式：

- 建立用户、个人经营簿及其唯一所有者关系。
- 在成员结构中预留模块权限字段，个人版由本人管理自己的业务，界面不展示权限档位设置。
- 预留项目成员结构；经营簿内的个人经营项目可以记录创建者的管理关系。
- 明确账号私有数据的归属字段；个人能力提升内容不通过团队成员关系获得访问权。
- 预留后续需要的归属约束、业务编号作用范围和查询入口，不实现团队操作流程。

第一版不实施：

- 创建团队、升级团队版、团队或项目邀请、多人加入、成员退出及交接操作。
- 团队模块授权界面、项目成员授权界面、多人协作业务流程。
- 团队共享经验库或能力提升共享。
- 复杂角色配置、逐条客户或订单授权、多人实时共同编辑。
- 团队订阅、席位收费或套餐体系；3–5 人是目标使用场景，不是已确认的硬性人数上限。

本文中的权限矩阵描述未来团队版的操作资格，不构成第一版新增功能入口的施工需求。例如，团队规则约定可编辑成员能编辑和删除日志，不据此自动给第一版增加原个人需求中未安排的功能。

第一版功能范围已确认为原 App v1.0–v1.4 的全部功能，加用户名注册登录、密码管理及人工找回，并采用已确认通用名称。具体内容见[第一版功能需求整合](第一版功能需求整合.md)，名称见[模块与字段命名清单](模块与字段命名清单.md)。本文件负责数据库与权限规则，不扩大功能范围。

## 2. 产品背景、技术方向与开发部署顺序

### 2.1 产品背景

农场经营簿面向 OPC、一人公司和创业者，连接客户跟进、项目交付、待办执行、订单回款、经验与复盘积累。

原版为个人使用的 Mac 桌面软件，采用 Electron、React、SQLite 及本机 Agent API。网页版是新的 Next.js 全栈产品，继承原版产品理念和业务规则，重新设计账号、数据归属及服务部署。

当前确定的业务板块：

1. 客户。
2. 账房。
3. 订单。
4. 项目及待办，即农场与农活。
5. 经验与认知沉淀。
6. 能力提升。

农场名称、区域及语言体系属于产品组织方式；权限判断使用稳定的数据归属和成员关系，不依赖名称、区域文案或页面导航。

### 2.2 技术方向

| 项目 | 当前结论 |
|---|---|
| 应用技术栈 | 已确认 Next.js 全栈 |
| 数据库 | 已认可 PostgreSQL，作为首选方案 |
| Agent 能力 | 已确认支持 Agent 辅助读取、写入 |
| 首批用户地域 | 中国大陆为主 |
| 部署方向 | 建议国内云托管，应用和数据库优先部署在同一地域 |
| SaaS 框架首选 | Velobase Harness，保留 AI SaaS 扩展能力，一期按最小 MVP 启用 |
| 数据访问 | 优先沿用框架 Prisma；正式交付包含可部署的版本化迁移 |
| 认证 | 适配框架认证为用户名＋密码、自助注册和人工找回；默认邮箱白名单密码登录不能直接交付 |
| 辅助基础设施 | 原框架依赖 Redis，负责限流等辅助能力，不替代 PostgreSQL；一期优先只运行 Next.js Web，不默认运行 Worker 或独立 Hono 服务 |
| 云厂商、实例规格、组件最终版本 | 后续施工验证并记录；本地与云端隔离，正式上线另行验收 |

PostgreSQL 是数据库引擎，云托管是运行和维护方式。开发期间可以在 Mac 本地运行 PostgreSQL，不必从一开始连接云数据库。

### 2.3 开发与部署顺序

1. 明确个人版施工范围。
2. 本地 Next.js 连接本地 PostgreSQL，跑通身份识别、个人经营数据读写和授权 Agent 调用的最小闭环。
3. 尽早做一次云端测试部署，验证真实网络环境下的登录、配置、数据连接及 Agent 调用。
4. 继续在本地开发，并定期在云端测试环境验证。
5. 个人版验收后，再部署正式环境并邀请少量用户使用。

本地开发、云端测试、正式环境的数据和凭据分别管理。本地开发不直接操作正式用户数据库；测试数据不整库复制为正式数据。

本地与云端尽量使用一致的 PostgreSQL 主版本及所用功能。用版本化 migration（数据库结构迁移）维护表、字段、索引和约束，在不同环境执行同一套结构变更；部署代码不覆盖正式经营数据。

## 3. 数据归属：用户账号、经营簿、项目

### 3.1 三个基础概念

| 概念 | 负责内容 |
|---|---|
| 用户账号 | 谁登录、谁操作，以及个人私有内容属于谁 |
| 经营簿 | 客户、订单、收入及经营项目等业务数据属于哪里 |
| 成员关系 | 哪个用户可以进入哪本经营簿，以及拥有的模块权限 |

第一版注册或初始化时，为用户建立个人经营簿，并建立该用户作为唯一所有者的成员关系。后续团队版通过扩展成员关系支持多人使用同一本经营簿。

### 3.2 经营簿业务数据

- 客户、订单、收入、经营项目等业务数据具有明确的 `workspace_id`（经营簿 ID）。
- 业务关联必须在允许的归属范围内建立。不同经营簿的客户、订单、项目等不能互相关联。
- 谁创建记录与记录属于哪里分别保存。`created_by`（创建人）及 `updated_by`（最后修改人）不替代业务数据归属。
- 成员退出团队后，团队业务数据及其历史操作继续保留；原创建人身份不自动赋予持续访问权。
- 经营簿所有者身份不自动赋予未加入项目的访问权，也不赋予他人个人私有内容的查看权。

### 3.3 账号私有数据

以下内容归属于用户账号：

- 经验与认知沉淀，包括适用的个人经验和复盘记录。
- 能力提升内容，以及其项目、日志和待办。
- 普通未关联项目、也未作为客户跟进事项的个人待办。

使用 `owner_user_id`（所属用户 ID）等明确字段标识个人归属。账号私有内容的访问不以团队成员关系仍有效为前提；用户退出、更换团队后仍可访问自己的内容。

团队创建者和其他成员均不能在产品内查看他人的个人内容；个人内容不向其他成员提供名称或内容摘要。未来团队共享经验库留待新版本，第一版不实施。

### 3.4 同一表支持两种数据归属

项目与待办可复用原模型，同时明确区分：

- 经营簿内的经营项目及项目农活。
- 账号私有的能力提升项目、其日志和待办。

可用 `access_scope`（访问范围）区分上述用途：经营簿项目必须有经营簿归属；账号私有内容必须有所属用户，其访问不能依赖团队经营簿。字段名和枚举值属于工程实现选择，归属语义必须保持一致。

附属日志和资料链接继承所属记录的归属。个人项目不能因为关联团队数据或被团队成员查询而变成共享内容；第一版不提供个人与团队之间的数据转移功能。

原版 v1.4.0 建表定义共包含 20 张表。下表是已有职责盘点，供 PostgreSQL 设计复用，不要求逐字复制 SQLite 的 SQL。

| 序号 | 中文名称 | 原表名 | 主要职责 | 网页版适配方向 |
|---|---|---|---|---|

## 5. 新增基础与预留结构

### 5.1 核心结构

| 表名 | 中文名称 | 主要内容 | 第一版落实方式 |
|---|---|---|---|
| `users` | 用户 | 用户身份、账号状态，衔接认证机制 | 落实个人账号身份与隔离 |
| `workspaces` | 经营簿 | 经营簿身份、名称、状态及个人／团队类型预留 | 只创建个人经营簿；团队类型不开放使用 |
| `workspace_members` | 经营簿成员 | 用户、经营簿、成员状态、所有者身份、模块权限 | 每本个人经营簿只有本人这一位所有者；不开放成员管理 |
| `project_members` | 项目成员 | 项目、用户、项目权限及有效状态 | 预留结构，可初始化本人管理关系；不开放协作与授权流程 |

核心成员约束：

- 同一用户在同一本经营簿只有一条当前成员关系，历史状态按所选实现保留。
- 同一用户在同一项目只有一条当前成员关系。
- 团队项目成员必须是该经营簿的有效成员；约束与服务校验共同保证。
- 项目成员关系只对应经营簿内项目，不用于让其他成员访问账号私有能力项目。
- 第一版不为权限档位分别建表，也不建立可自定义角色和权限配置系统。

### 5.2 审计提出的支撑结构

以下两张表是此前审计建议的支撑方式，不代表已经固定了认证组件和物理表方案。技术 Agent 应围绕个人版 Agent 读写及重要操作追溯采用最小实现，并说明选型。

| 建议表名 | 中文名称 | 目的 | 边界 |
|---|---|---|---|
| `agent_credentials` | Agent 凭据 | 凭据摘要、授权用户、允许范围、有效期及撤销状态 | 独立 API 凭据方案可采用；外部授权服务承担职责时可复用其能力 |
| `audit_logs` | 操作日志 | 执行者、网页／Agent 来源、目标及重要字段变化 | 服务重要操作追溯，不实施独立审计产品或团队审计面板 |

登录会话等认证辅助表数量由后续认证方案决定。团队邀请表 `workspace_invitations` 属于后续团队邀请功能的可能实现，第一版不搭建邀请流程。

### 5.3 表数量的解释

- 原版已有表：20 张。
- 用户、经营簿、经营簿成员三个基础概念：新增 3 张。
- 本轮项目级权限：再预留 1 张项目成员表。
- 审计建议的 Agent 凭据、操作日志：另有 2 张支撑表方案。
- 若保留原有职责并采用全部核心及支撑结构，可暂估 26 张。

**表数是职责盘点结果，不是必须达到的验收指标。** 最终物理表数受认证实现、元信息用途和支撑结构复用影响。不能为了凑表数新增功能，也不能只根据表数认定数据隔离及权限正确。

## 6. 通用模块权限：后续团队版规则

客户、账房、订单分别授权，每位成员可以在三个模块拥有不同档位。

| 权限 | 查看 | 新增 | 编辑／更正 | 删除／恢复 |
|---|---|---|---|---|
| 无权限 | 不允许 | 不允许 | 不允许 | 不允许 |
| 仅可查看 | 允许 | 不允许 | 不允许 | 不允许 |
| 可编辑 | 允许 | 允许 | 允许 | 不允许 |
| 可管理 | 允许 | 允许 | 允许 | 允许 |

可在经营簿成员结构中预留：

- `customer_permission`：客户权限。
- `finance_permission`：账房权限。
- `order_permission`：订单权限。

每个字段使用固定四档，具体数据库枚举名称由技术 Agent 统一确定。普通业务权限不合并为一个总开关，账房权限不只用可见／不可见一个布尔字段替代四档。

个人版由本人管理自己的业务，不展示权限设置。平台仍须识别本人身份及数据归属；“个人版没有权限档位区分”不等于所有用户可以访问同一份数据。

### 6.1 客户、账房、订单的职责边界

- 客户权限控制客户完整资料、适用的沟通及客户跟进操作。
- 账房权限控制收入流水、收款明细等账房内容。
- 除经营簿所有者及被明确授予账房权限的成员外，其他成员不能查看账房内容。
- 订单权限控制订单完整资料及订单操作。
- 团队创建者默认作为经营簿所有者，负责邀请经营簿成员及调整模块授权。
- 模块中的“可管理”控制业务记录操作，不自动赋予经营簿成员邀请或模块授权权力。

### 6.2 订单与账房金额可见性

已确认：有订单查看权限，即可查看该订单的约定金额、已到账合计和应收金额，即使没有账房权限。

- 展示订单已到账合计不授予逐笔收入流水查看权。
- 客户详情中的财务汇总受订单查看权限控制。
- 首页累计收入、本月到账等整体收入统计受账房查看权限控制。
- 汇总由服务端依据业务规则计算；订单权限不能通过修改汇总字段变更实际收入。
- 无权查看的财务字段应按授权规则省略或隐藏，不返回零值冒充真实金额。

## 7. 项目及农活权限：后续团队版规则

本节适用于经营簿内的协作项目；账号私有的能力提升项目按第 3 节处理。协作项目单独选择参与成员并设置项目权限。经营簿成员身份不自动等于项目成员身份；未加入项目的成员看不到项目及其日志、关联农活。

| 项目操作 | 无权限／未加入 | 仅可查看 | 可编辑 | 可管理 |
|---|---|---|---|---|
| 查看项目、日志和项目农活 | 不允许 | 允许 | 允许 | 允许 |
| 新增、编辑日志及项目农活 | 不允许 | 不允许 | 允许 | 允许 |
| 删除、恢复日志及项目农活 | 不允许 | 不允许 | 允许 | 允许 |
| 修改项目基础信息 | 不允许 | 不允许 | 不允许 | 允许 |
| 删除、恢复项目 | 不允许 | 不允许 | 不允许 | 允许 |
| 邀请成员加入项目 | 不允许 | 不允许 | 不允许 | 允许 |
| 调整成员的项目权限 | 不允许 | 不允许 | 不允许 | 允许 |

项目基础信息包括项目名称、说明、状态、开始日期和目标完成日期等基础字段，仅项目可管理成员可以修改。

项目可编辑成员可以删除日志及农活，但不能修改项目基础信息或删除项目。这是已确认的项目规则，与客户、订单、账房模块的编辑档位分别执行。

项目管理者只管理自己项目的成员权限，不因此获得其他项目、客户、订单、账房或经营簿整体授权能力。邀请项目成员遵循第 5 节中的有效经营簿成员前提；第一版不实施邀请。

### 7.1 管理员交接与项目解散

- 每个有效协作项目至少保留一位可管理成员。
- 最后一位管理员退出项目或降权前，先交接管理权；也可以直接解散项目。
- 解散按可恢复删除处理，保留项目、日志、农活和权限历史。
- 解散后保留最后一位管理员的恢复权限；如该管理员还要退出团队，必须先移交恢复权限。
- 恢复负责人应明确可追溯，可通过项目成员关系或项目字段表达，不能由“谁最早创建”等隐含判断替代。
- 恢复时沿用原有权限，并检查成员当前仍有效；恢复项目不重新激活已经退出团队或已经被撤销的成员权限。
- 管理员交接、最后管理员校验及解散操作需要保持一致，不能因同时操作产生无人管理的有效项目。

上述多人流程只记录为后续团队规则，第一版不实现管理员交接或项目解散后的团队恢复交接界面。

### 7.2 项目日志

- 每条耕种日志独立保存，记录所属项目、业务日期、内容和创建时间。
- 日志继承项目访问范围，项目改名或改区域不改变关联。
- 排序保持日志日期倒序、创建时间倒序及稳定的次级排序；同一天允许多条日志。
- 结构预留编辑所需的版本号、更新时间及修改人，删除采用可恢复删除。
- 追加日志不自动修改项目状态或其他项目字段。
- 项目删除后冻结其日志和农活写入；恢复项目后重新开放符合权限的访问与写入。
- 第一版只交付个人需求中确定的日志操作，不因团队权限矩阵增加编辑、删除功能入口。

### 7.3 未关联项目的农活

按以下顺序确定访问规则：

1. 关联项目的农活，遵循所属项目权限；能力提升项目下的农活仅本人访问。
2. 未关联项目、属于客户跟进的农活，继承客户权限。
3. 普通未归属项目的个人待办，仅本人可见，归属于个人账号。

同时关联项目和客户的农活按项目规则控制农活访问；关联客户的摘要与详情继续按各自规则处理。

原版合作方跟进结构保留为个人数据职责；本文不自动新增合作方团队权限规则。

## 8. 名称摘要、完整详情及关联关系

已确认的摘要规则：

| 关联内容 | 摘要规则 | 完整详情规则 |
|---|---|---|
| 客户 | 在有权查看的记录中，可展示关联客户名称 | 打开完整客户详情仍需客户权限 |
| 订单 | 在有权查看的记录中，可展示关联订单名称 | 打开订单详情及查看财务字段仍需对应权限 |
| 经营簿项目 | 仅项目成员可看到项目名称 | 未加入项目不可访问项目详情、日志及农活 |
| 个人沉淀、能力提升 | 不向其他成员提供摘要 | 仅所属用户访问 |

例：能看订单但不能看客户的成员，可以看到订单对应的客户名称，但不能打开客户完整详情。

摘要例外仅允许在同一本经营簿、且当前主记录本身可访问的情况下提供。它不授予整个客户或订单列表的浏览、搜索、导出或任意查询能力，也不授予编辑关联目标的权限。

客户名称摘要不包含联系方式、需求、沟通记录等完整资料；订单名称摘要不包含订单金额、到账、应收或收入明细。

关联不是授权。不能因为能访问订单、客户或项目中的一个对象，就自动获取它关联的其他对象详情。

## 9. ID、唯一规则、日期和数据字段

### 9.1 内部 ID 与业务编号

- 内部记录使用全局唯一且不可变的 ID；业务编号作为展示和引用编号，和内部 ID 分开。
- 外键及实际关联以稳定内部 ID 为依据，名称、状态、区域变化不影响关联。
- 经营簿数据的业务编号在经营簿范围内唯一；个人数据的业务编号在个人账号范围内唯一。
- 不同用户或经营簿可以拥有相同展示编号，接口不能仅凭展示编号进行跨归属查询或更新。
- 原版前缀作为参考：客户 `KH`、合作方 `HZ`、项目 `XM`、农活 `BL`、订单 `OD`、收入 `SR`、资料 `ZL`、经验 `JYBX`、产品 `CPBX`；复盘为 `WeekR`、`MonthR`、`QuarterR`。
- 原日期型编号以北京时间创建日期及实体当日序号生成，项目编号按原区域序列生成；私有复盘编号以复盘类型及复盘日期生成。
- 编号生成后固定，删除不复用；项目调整区域保留原编号，区域另存字段。
- 编号递增采用并发安全的数据库操作，不能读取旧值后在应用中直接加一而不处理竞争。

### 9.2 复盘唯一性

私有复盘按“所属用户＋复盘类型＋复盘日期”唯一，允许不同用户同日各有一份同类型复盘。

- 同用户同类型同日期重复录入，定位已有记录继续编辑，不覆盖原正文、不创建重复记录。
- 数据接口返回明确重复提示并提供调用者有权访问的已有记录。
- 正文保存 Markdown 源文本，阅读时安全渲染。
- 沿用原版身份稳定规则：已保存记录的类型、日期保持不变，普通正文编辑不改变 ID 或编号。

### 9.3 通用字段及日期

- 主要可编辑业务记录保存内部 ID、版本号、创建时间、更新时间和删除标记；记录创建人、最后修改人。
- 可编辑附属记录按实际操作需要保存版本、修改和删除信息。
- 业务日期按 `YYYY-MM-DD` 表达；计划日期、截止日期、到账日期、复盘日期和日志日期保留日历日期语义。
- 事件时间记录明确时间戳；接口使用 ISO 8601，统计及日期型业务编号沿用 `Asia/Shanghai`。
- PostgreSQL 可采用 `DATE` 保存业务日期、`TIMESTAMPTZ` 保存事件时间。具体字段类型属于工程选择，语义必须一致。
- 默认查询及统计不包含已删除业务记录；授权的查看已删除与恢复操作另行处理。

## 10. 订单、收入和农活的业务一致性

### 10.1 关系及金额

- 客户、合作方、项目、农活、订单、收入、资料及其关联沿用原业务职责。
- 项目可关联多个客户、合作方及订单；订单关联一个客户，并可关联多个项目。
- 一张订单可以关联多笔收入；收入也可以独立登记，不必关联订单。
- 订单交付状态和收款状态分别管理。
- 金额以整数分保存、计算及传输，不采用浮点元计算；PostgreSQL 选用足够范围的整数类型，并处理好 API 数值转换。
- 收入金额为正；订单金额未知用空值表达，与零区分。
- 订单已收金额为关联有效收入之和，应收金额为订单金额减去已收金额。
- 多收时保存真实收入，应收可为负，明确标记多收；未知订单金额不推断为已收齐。
- 累计收入、本月到账包含未关联订单的有效收入；本月按实际到账日期统计。
- 收入更正、删除、恢复及重新关联后，统一重新计算订单、客户及首页相关汇总。
- 删除客户、订单或项目不删除已发生的有效收入。删除订单后，已发生收入及历史客户归属仍需保留。
- 取消订单保留历史实际收入；当前应收与历史到账分别按统一口径计算。
- 汇总采用同一业务服务，不能由网页、Agent 分别维护独立金额口径。

例：10,000 元订单关联 3,000 元及 2,000 元有效收入后，已收 5,000 元，应收 5,000 元。

### 10.2 农活状态和历史

- 优先级沿用 P0／P1／P2，默认 P1。
- 项目详情和统一农活列表展示同一份农活数据，不复制两套记录。
- 完成时间取实际完成操作时间；历史农活按完成时间倒序，可按北京时间完成日期筛选。
- 取消完成恢复完成前状态并清空当前完成时间；再次完成记录新的完成时间。
- 项目状态与农活状态分别保存。修改项目状态不自动批量改变农活状态。
- 完成、删除、放弃是不同含义；完成事项保留在历史数据中。

## 11. 删除、恢复及成员生命周期

### 11.1 可恢复删除

- 业务删除采用软删除，保留 ID、关联及历史数据，删除前有确认。
- 删除权限包含恢复权限；恢复沿用原 ID 和业务编号。
- 删除收入后从有效收入汇总中剔除；恢复后重新计入。
- 项目删除或解散后冻结子记录写入，不物理级联清除日志和农活；恢复项目后恢复授权访问。
- 父项目恢复不自动恢复已经单独删除的日志或农活，也不重新激活失效成员。
- 团队版可编辑成员能删除、恢复日志和农活；仅项目可管理成员能删除、恢复项目。
- 第一版不增加永久清除历史数据的操作。

### 11.2 成员撤权与历史保留

- 团队成员被移除、退出或权限降低后，后续请求应执行其当前权限。
- 旧页面、旧登录状态和旧 Agent 凭据不能继续执行已被撤销的权限。
- 成员退出不删除其历史创建的团队业务记录和操作来源。
- 项目可管理成员可以调整所属项目权限，但不能提升经营簿模块权限。
- 私有内容属于用户账号，退出团队不失去本人私有内容。

第一版每本个人经营簿只有所属用户这一位成员，不提供上述团队生命周期操作；归属模型及查询组织应能承接后续规则。

## 12. Agent、并发、请求去重与操作追溯

### 12.1 网页与 Agent 共用业务服务

- 网页和 Agent 调用同一套业务校验、权限判断、金额汇总、关联校验及状态规则。
- Agent 通过授权 API 读写，不直接获得数据库管理员凭据。
- Agent 按稳定内部 ID 和明确归属操作数据，使用读取时的版本。
- 是否接单、放弃项目、变更经营决定、删除记录等由人类决定；Agent 根据明确指令执行。
- 保留清晰的实体字段、查询参数、分页、排序、错误和版本契约。
- 原版 loopback 及本机凭据文件是桌面运行方式；网页版按远程授权场景实现，不照搬单个本机 Token 作为全平台权限。

### 12.2 Agent 授权

- 凭据绑定授权用户，明确允许的个人或经营簿范围及读写操作。
- 实际权限取凭据允许范围与授权用户当前有效权限的交集。
- 用户不能看账房时，其 Agent 也不能读取收入流水；允许读取订单时，按已确认订单规则返回金额合计。
- 项目和私有内容遵循相同权限，不因 Agent 入口获得额外访问权。
- 支持凭据到期及撤销，不将原始凭据写入日志、文档、对话或仓库。
- 独立凭据方案只保存必要的凭据摘要及授权元信息，具体认证实现由后续施工选型。

第一版只开放本人授权的个人数据访问，不开放团队授权管理功能。

### 12.3 版本冲突与事务

- 更新、删除、恢复及农活状态变更检查读取时的版本。
- 保存时由数据库同时验证版本并执行更新，或采用明确的锁定方案；不能仅依赖应用层先读取再比较。
- 记录字段及关联变化在同一事务内提交，失败整体回滚。
- 发生冲突时返回最新的授权数据，网页保留草稿，Agent 重新读取后处理，不静默覆盖。
- 局部更新区分未提交字段与明确清空字段。
- PostgreSQL 的并发语义需要重新验证，不能认定原 SQLite 事务代码可直接复制。

### 12.4 请求去重

- 新增记录、登记收入、追加沟通及追加日志等支持幂等请求。
- 同一次提交的重试使用相同请求标识；不能生成第二条业务记录。
- 去重范围包含数据归属、调用身份和操作，避免不同用户或经营簿共用键导致串数据。
- 同一个请求标识提交不同请求内容应返回明确冲突，不复用旧响应冒充成功。
- 去重与实际写入保持事务一致，并正确处理同时到达的重复请求。
- 返回历史响应前仍校验当前权限，撤权后不能通过去重缓存读取旧响应。

### 12.5 操作追溯及错误

- 重要收入变更、业务删除恢复、成员或权限变化具备可追溯的执行者、时间、来源、对象及关键字段变化。
- 创建人、最后修改人不能替代逐次重要操作历史。
- 日志读取继承对应数据的可见规则，不通过日志泄露收入明细、不可见项目或个人内容。
- 追溯记录不包含原始访问凭据；普通业务操作不能随意改写历史追溯内容。
- 明确区分校验失败、认证失败、权限不足、未找到、版本冲突、重复复盘、请求内容冲突及服务错误。
- 错误中的最新记录、排序结果、计数、搜索及导出同样执行数据归属及权限规则。

## 13. 隔离、索引、资料和备份

### 13.1 约束与查询

- 经营簿归属和用户私有归属由服务端验证，普通编辑不能改变记录归属。
- 关系表的约束覆盖归属，防止一端属于甲经营簿、另一端属于乙经营簿。
- 资料链接、沟通等按类型关联对象的结构，在统一服务内校验对象存在、归属与权限，不只校验对象 ID 字符串。
- 外键、唯一约束、版本条件更新和索引共同支持正确性。
- 列表、详情、首页数字、搜索、统计、日志、导出、已删除记录、恢复及 Agent API 均执行相同范围限制。
- 可使用 PostgreSQL RLS（行级安全）作为数据库层保护。RLS 必须配合正确策略和数据库访问角色，不能仅增加归属字段或用绕过策略的高权限角色就声称隔离有效。
- 经营簿数据索引围绕归属加常用筛选／排序字段建立；私有数据围绕所属用户建立；项目成员、模块成员及去重查找具有合适索引。

### 13.2 外部资料的指针与链接

- 已确认外部资料只保存指针与链接，文件由用户在本地或原网站保管；服务器保存名称、地址、分类、用途、备注、关联等轻量索引。
- 沿用 `resources`、`material_links` 和 `resource_projects` 的既有职责。地址可指向网页、本地文档或 Obsidian 笔记，归属与读取权限继承所属业务记录；此规则不新增附件正文、附件表或对象存储管理。
- 第一版必须一键唤起普通本地文档，用户已接受安装本机配套工具。云端保存指针，本机工具在当前设备使用系统默认关联应用打开文件；具体技术形态参照[第一版功能需求整合](第一版功能需求整合.md)第 9.1.1 节。
- 保留 Mac／Windows 路径及 Obsidian URI 的真实含义，不把本地文件指针解释成云端服务器路径。当前设备是否拥有目标文件，与资料索引是否存在分别判断。
- 删除、恢复或更正资料索引只作用于索引数据和关联；原文件继续由用户保管。
- 链接在同一账号不同设备上可读取，但本地文档及 Obsidian 笔记的打开要求该设备拥有对应文件、应用和配置；未来团队权限同样只授予索引访问，不自动转为文件访问权。
- Agent 经授权读写资料索引；读取原网站或本地文件正文，需要另有相应来源与设备访问授权。
- 第一版不提供外部资料文件上传、云端附件托管或自动同步文件内容。应用内业务记录、经验与复盘正文仍按已有数据库规则持久化。

### 13.3 备份和恢复

- 数据独立于代码和部署产物；更新代码不重建或覆盖经营数据。
- 使用一致性备份；结构升级、重要恢复操作前保留可恢复路径。
- 原桌面版每日备份及最近 7 个日期的保留策略可作参考，云端实际备份配置、保留周期及恢复能力在部署时明确。
- 验证备份可恢复，恢复失败时保护现有可用数据。
- 整库灾难恢复由平台运维处理；不能让某个用户恢复自己的经营簿时覆盖其他用户数据。
- 已确认个人备份下载包含本人经营数据、账号私有内容、必要关联及资料指针；不含外部文件、账号密码、会话、Agent 密钥或平台秘密。
- 恢复采用单用户回滚：当前有效业务内容回到备份时点，备份后新增内容退出当前有效视图但保留历史。归属映射始终由当前身份确定，不能信任备份中提供的其他用户或经营簿 ID。
- 恢复前校验格式、版本、引用和归属，明确显示覆盖范围；先保存当前一致性快照并再次确认。快照成功后才进入恢复，失败保护原数据。
- 以账号／个人经营簿为范围阻止并发写入，在事务或等价一致性方案中恢复；其他用户继续可用。刷新数据视图并使恢复前旧版本、旧标签页和延迟 Agent 写请求失效，不能因版本号回退让旧请求重新有效。
- 内部 ID、已占用业务编号、序号高水位及追溯记录保持稳定；不因回滚重新发放已用编号。恢复自身可追溯，审计历史不随业务快照回滚或从外部备份伪造。
- 备份结构版本、兼容校验和保存当前快照的技术形态由实施方案明确。用户恢复只影响本人业务；平台整库灾难恢复属于运维职责。

### 13.4 框架与业务模型边界

- 原版 20 张表是业务职责盘点，不是必须照搬的物理表数量。用户名认证、授权与审计支撑结构以实际方案为准。
- 框架 SaaS 商品／订阅订单／支付模型与本产品客户订单、收入流水及产品资产库分别建模。框架 AI 项目和文档组织结构也不直接替代经营项目、日志及外部资料指针。
- 可复用框架用户和认证基础；新增用户名及个人经营簿归属规则。框架全局管理员字段不授予读取用户私有经验、复盘或能力提升内容的业务权限。
- 保留 AI、计费、模型供应商等未来扩展源码与定义；第一版不调用这些业务，也不据框架自带模型新增产品功能。实施时记录必要表、预留表及未启用模型，避免把默认整套演示迁移与种子当成业务需求。

## 14. 验收：第一版与后续团队版分开

### 14.1 第一版必须验证

1. 两个独立账号的数据互相隔离，不能通过 ID、列表、关联、汇总、错误或 Agent 获取另一账号数据。
2. 每个个人经营簿只关联本人这一位所有者，不提供团队创建、邀请和授权入口或可调用的团队操作接口。
3. 个人沉淀、复盘、能力提升及个人待办具有账号归属，访问不依赖某个团队成员关系。
4. 首次个人经营数据为空；验证使用独立环境和虚构数据，保护原 App 数据。
5. 关联、收入汇总、未知金额、多收、删除恢复及农活历史符合统一口径。
6. 用户与 Agent 同时修改时，旧版本更新返回冲突；重复请求不重复登记收入或日志。
7. 两个用户同日创建相同业务编号、同类型复盘，不互相冲突；同用户重复复盘遵循唯一规则。
8. 原始凭据不进入日志；撤销个人 Agent 凭据后不能继续访问。
9. 数据库迁移可在本地与云端测试环境执行，升级保留数据；备份恢复验证通过。
10. 预留的经营簿成员、项目成员及权限字段结构清楚，团队流程没有被提前实现。

第一版不要求执行完整的多人团队场景验收；应核验结构是否承接规则，不为测试预留结构而开发团队业务功能。

### 14.2 后续团队版实施时验证

- 四档模块权限逐项正确，网页与直接 API 调用结果一致。
- 订单金额合计、客户财务汇总、首页收入统计及收入明细遵循各自规则。
- 未加入项目不可见名称、日志和农活；只读不可写，编辑者可删除子记录但不可修改或删除项目。
- 项目管理者可邀请和调整本项目成员，不能修改经营簿模块授权。
- 私有内容不向经营簿所有者、其他成员及其 Agent 暴露摘要或详情。
- 退出或撤权后，旧页面、旧请求及旧 Agent 立即不能执行已撤销权限。
- 最后管理员交接、解散及恢复权限移交规则成立，恢复不重新激活失效成员。
- 关联名称摘要仅提供已确认范围，不扩大成完整资料访问。

实际稳定性还需根据整个平台的用户量、请求量及部署配置做负载验证；每个团队 3–5 人不等于平台总共只有 3–5 人。
