## 1. 本版目标和文档入口

光域空间是光域工作室的 OPC 经营管理工具，Slogan 为“让事业，多一种可能”。用户以可视化界面管理经营记录，并可授权 Agent 读取与写入同一份业务数据。首批用户以中国大陆为主。

第一版只实现个人版，支持多个独立账号在线使用各自的数据。保留团队与 AI SaaS 的未来扩展框架，以最小 MVP 的运行与实现方式完成已经确认的原 App 业务范围。

## 3. 三个框架的选型研究

### 3.1 调研方法和限制

读取 ShipAny、ShipFast 的官方产品页、技术文档和许可；两者当前商业产品的私有付费源码未获取，不能声称完成源码审计。

Velobase 官方仓库可公开读取，已在项目外临时目录进行源码静态检查，未安装依赖、运行应用或测试。核对 User、认证、Prisma 模型、模块组合、Redis、服务启动和 Harness 设计／测试／交付规则。

核对基准：[Velobase 提交 ed6c832](https://github.com/velobase/velobase-harness/tree/ed6c8324fdc34fcd0e64f1e9da4bef847830605b)，提交日期 2026-10-13，源码 package 版本 0.2.0。源代码的 Next.js 依赖为 `^15.5.25`、NextAuth 为 `5.0.0-beta.32`、Prisma 为 `^6.5.0`，pnpm 为 10.12.1；安装结果以锁文件为准。选择提交基准不等于运行质量已经验证，开工须重新核对安全公告与依赖兼容性。

### 3.2 对比与结论

| 维度 | ShipAny：以当前 Next 产品线为准 | ShipFast | Velobase Harness |
|---|---|---|---|
| 获取和许可 | 商业源码许可，当前完整模板需授权访问 | 商业源码许可，购买后访问 | 公开仓库、MIT；可自行托管和商业化 |
| 已选技术栈适配 | Next.js＋Drizzle，多数据库含 PostgreSQL | Next.js，公开数据库教程重点为 MongoDB／Mongoose，亦有 Supabase 方向；通用 PostgreSQL 需适配 | Next.js＋Prisma＋PostgreSQL，直接匹配数据库方向 |
| 开发 Agent 工作方式 | 提供 AGENTS／CLAUDE 与内置开发 Skills | 能用于 AI 辅助开发；公开材料不足以确认同等完整 Harness | 提供设计、模块建设、测试和完成检查规则，可复用 |
| 当前用户名注册 | 默认邮箱密码／OAuth，仍需适配 | 登录与数据库需按本产品调整 | 有密码登录代码，但当前是邮箱白名单，不是用户名自助注册；需适配 |
| CRM 和个人数据隔离 | 需实现本产品领域模型；模板 RBAC 不等于经营簿权限 | 需实现本产品领域模型 | 有扩展点；现有 SaaS／AI 领域表不能直接作为本产品 CRM 表 |
| 国内自托管 | Next 产品线有 Docker 部署文档 | Next.js 可选择适合的宿主，需修改默认外部服务配置 | 可自行部署，不要求使用官方 Cloud 或 Launchpad |
| AI SaaS 后续扩展 | 支付、积分、AI 等引擎能力 | 偏通用 SaaS 启动、登录、支付、邮件和营销页面 | 已有模型适配、AI、计费、积分、订阅等源码，方便未来按需启用 |
| 当前主要成本 | 付费源码及未能核实的实际裁剪成本 | 数据库／认证适配，契合度较低 | 模板较重、静态依赖仍在；精简启动和领域隔离须实测 |
| 本项目选择 | 第二备选 | 暂不优先 | **已确认首选，按最小 MVP 接入** |

证据：[ShipAny Next 技术与 Skills](https://shipany.ai/docs/shipany-next)、[ShipAny Next 获取方式](https://shipany.ai/templates/shipany-next)、[ShipAny 许可](https://shipany.ai/license)、[ShipFast 官方介绍](https://shipfa.st/)、[ShipFast 数据库](https://shipfa.st/docs/features/database)、[ShipFast 许可](https://shipfa.st/license)、[Velobase 官方仓库](https://github.com/velobase/velobase-harness)。结论是结合本产品约束作出的选型判断，不是框架的 CRM 成品能力声明。

### 3.3 采用 Velobase 的具体边界

1. Harness 首先是约束开发 Agent 的设计、实现、测试和交付流程。上线后的经营 Agent API 单独建设，不能由模板 AI Chat、tRPC 登录检查或“有 Harness”直接替代。
2. 新业务按框架模块扩展点实现，Router 做校验和适配，服务负责归属及业务规则。网页和外部 API 复用同一服务，不建立两套订单计算。
3. 认证增加规范化唯一用户名、自助注册和受控人工重置；移除运行路径对邮箱白名单／邮件验证的强制依赖。禁用本地演示免密码登录的生产入口。
4. 框架 `Product/Order/Payment` 是平台收费领域；客户订单、实际收入和经营资产产品独立建模。框架 AI `Project/Document` 也不能直接替代本产品经营项目和指针资料。
5. 官方模块文档明确区分运行开关和代码可选性；源码根 Router、认证及部分服务仍静态引入旧模块。第一版建立仅含已启用能力的运行组合，检查页面、API、Server Actions、Webhook、事件订阅和调度均符合范围。关闭导航不能替代服务端限制。
6. 原运行路径依赖 Redis（如限流），即使只运行 Web 也不能直接假设完全不需要 Redis。最小基线为 Next.js Web＋PostgreSQL＋必要 Redis；Worker／独立 Hono 默认不运行，所需备份调度选择最简单可验证的运维方式。
7. 保留 AI、计费、积分、订阅及供应商适配源码、许可和扩展文档。暂不启用、不配置真实服务密钥，不删除未来能力以换取表面上的精简。技术 Agent 不必为了“所有包可卸载”重构整个框架。
8. 框架新增 Electron／Expo 宿主仍在渐进抽取，Web 目前仍从仓库根运行。第一版以 Web 为主，本机资料打开单独做最小配套工具，不据此增加完整桌面或移动产品。
9. 不使用官方 Launchpad 自动建云资源／推送部署流程。本地开发、独立云测试和生产分开；云端操作在资源及授权明确后执行。

## 4. 一期范围与扩展保留

“最小 MVP”优先让用户完成一个经营闭环：注册登录 → 管理客户 → 建立项目与任务 → 登记订单及收入 → 沉淀和复盘；按详细需求补齐原版全部功能。工程实施可分阶段验证，最终验收不能用静态演示替代持久化业务。

一期启用：个人账号、经营业务、必要授权 API、本机资料打开、个人备份恢复、必要运行限流和追溯。团队、共享库、实时协作、平台付费、积分、AI Chat／生成、模型计费、营销邮件、推广、广告追踪、云附件和移动端留待后续版本。

未来能力以已有模块、明确数据边界和扩展接口保留；不预先开放页面或编写空壳业务流程。团队模块授权、项目权限和个人私有内容规则继续按数据库参照文档保留。

## 5. 施工顺序与验收

1. 保护现有 docs 和品牌资产，固定上游提交，读完领域设计及必要集成规则；将已确认信息映射到 Harness 的设计阶段，不重复索取已确认决定。
2. 优先验证最小真实运行：本地 PostgreSQL／必要 Redis、Web 启动、用户名注册登录、个人经营簿建立、两个账号隔离及一次授权 Agent 写入。先排除依赖、认证和模块组合阻碍。
3. 按详细需求完成业务闭环及其余原版功能；基于数据规则而不是框架默认业务表建模，生成版本化迁移。
4. 完成真实本机打开、备份回滚与关键异常验证；完善文档、环境示例、API 契约和部署运行说明。
5. 交付本地可验收版本、运行步骤、测试证据及未验证环境；不 commit／merge／push。云端测试准备尽早做，执行须具备用户提供的资源与授权；正式上线在用户验收后办理。

重点验收：注册初始为空；网页和直接 API 的账号隔离；金额与取消删除后收入口径；关联归属；版本冲突；收入／日志重试去重；复盘唯一性；任务完成历史；备份回滚、编号不复用和恢复前旧请求失效；Mac 和 Windows 本机打开与错误状态；禁用模块不能绕过入口执行；凭据撤销；迁移与构建；桌面及小屏视觉。

尚未跑通的环境必须如实注明。特别是缺少 Windows 或云资源时，不能把静态检查写成实际平台验证通过。最终上线前补齐相关实际验证与运维配置，不将它们伪装为当前已完成。
